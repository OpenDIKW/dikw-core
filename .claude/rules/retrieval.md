# Retrieval: Karpathy's rule and the rerank stage

Read these rules before you change search, fusion, rerank, retrieval config, or eval.

- **Karpathy's rule:** *scoping is deterministic, reasoning is probabilistic*. Navigation (source listing, chunk lookup, link traversal) is deterministic SQL/file I/O. LLMs enter only at synth — the engine-internal authoring leg that writes the K layer. **Answer synthesis is not a `dikw-core` verb**; `retrieve` returns ranked chunks + page refs and the agent layer runs its own LLM on the result. W layer is hand-written (no engine LLM call writes wisdom). The invariant forbids **generative LLM reasoning** on the read path, not learned **scoring** models: the optional cross-encoder reranker (below) is a deterministic `(query, chunk) → relevance` scorer — the same epistemic category as the embedding model already in retrieval — so it is part of *scoping* (re-ordering the deterministically-retrieved candidate set), not *reasoning*. An **LLM-as-reranker is deliberately excluded** (it would put generative reasoning on the read path). See `docs/adr/0006-reranker-deterministic-scoping.md`.
- **Optional rerank stage.** A `RerankProvider` (`providers/base.py`, impl `OpenAICompatReranker` in `providers/rerank.py` over the Jina/Cohere-compatible `/rerank` shape; built by `build_reranker`) reorders the fused candidates inside `HybridSearcher.search` — after RRF fusion + the source-diversity penalty, before the `[:limit]` truncation. It scores the top `retrieval.rerank_candidate_k` (default 40, clamped to ≥ `limit`) fused chunks, re-sorts by relevance, then truncates; the window's chunk records are reused for materialization (no second `get_chunks`), and `Hit.score` becomes the rerank score. It never adds chunks outside the fused pool (so `recall@100` is unchanged — a change there is a bug). **No storage adapter changes; `retrieve`'s response shape is unchanged.** Provider wiring (`rerank`/`rerank_model`/`rerank_base_url`/`rerank_api_key_env`/`rerank_timeout_seconds`/`rerank_batch_size`) lives on `ProviderConfig` (a validator requires the three wiring fields once `rerank` is set, like the `openai_codex` base-url validator); behavioural knobs (`rerank_enabled`, `rerank_candidate_k`) on `RetrievalConfig`. The `rerank_candidate_k` window is split into `rerank_batch_size` (default 16, Gitee-safe) batches per `/rerank` call — vendors cap the `documents` array (Gitee: ≤25), and a cross-encoder scores each `(query, doc)` independently so batching doesn't change scores. **On once configured** — unlike `graph_enabled` (default-off), `rerank_enabled` defaults `True`, so setting `provider.rerank` is the opt-in and a base that configures none runs no rerank leg; `rerank_enabled=False` is a kill switch (used by eval to A/B off-vs-on at one config). The default `dikw init` scaffold (`config.default_config`) now ships a Gitee `bge-m3` embedder **and** a Gitee `bge-reranker-v2-m3` reranker keyed by one `GITEE_API_KEY`, so a fresh base reranks out of the box (OpenAI has no `/rerank` endpoint, so the prior OpenAI embedding default couldn't ship a matching reranker). `api.retrieve` (and `eval/runner.py::_run_queries`) build the reranker via `build_reranker(cfg.provider)` and thread it into `from_config`; it's closed in a local `finally` (lifetime is the single retrieve call). **Read-path resilience:** a transient rerank failure (5xx/408/429/timeout/connect drop) degrades to the fused order (logged at **ERROR** — a configured leg that failed, no 500); a permanent `ProviderError` (401/403/404, bad model/key) propagates so a misconfig fails fast — same classification as the embedding path. A transient **query-embedding** failure degrades the same way (the vec leg drops, FTS + graph carry the hybrid query, logged at ERROR), but **only in hybrid mode** — single-leg `vector`/`bm25` ablations have no FTS to fall back to, so they re-raise (eval purity); a permanent query-embed error always propagates (→ 500). An enabled-but-unconfigured reranker (`rerank_enabled` set, `provider.rerank` None) logs one **WARNING** per retrieve so the silently-off leg is visible (`api_retrieve._retrieve_inner`).
